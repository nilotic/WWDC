## 한 줄 요약

이 세션은 앱의 기능, 메뉴, 설정, 탭에 붙이는 이름을 **앱에 어울리는가**, **올바른 기대를 만드는가**, **언어와 플랫폼이 달라도 유지되는가**라는 세 가지 기준으로 평가하고, 사용자가 무엇을 생각하고 느끼고 행동하기를 원하는지부터 출발해 적절한 이름을 만드는 과정을 설명한다.

---

## 핵심 요약

이름은 인터페이스에서 작아 보이는 요소지만, 사용자가 앱을 이해하고 탐색하고 신뢰하는 방식에 직접 영향을 준다.

세션은 좋은 이름을 만들기 위한 흐름을 세 단계로 정리한다.

🧭 **Criteria**
   - 앱의 언어 체계에 자연스럽게 속하는가
   - 이름이 만든 기대와 실제 기능이 일치하는가
   - 다른 언어, 시장, 플랫폼에서도 문제없이 작동하는가

🛠️ **Process**
   - 먼저 대상 사용자를 명확히 정의
   - 사용자가 기능을 만났을 때 무엇을 생각하고, 느끼고, 행동하기를 원하는지 정리
   - 반복되는 주제를 묶어 이름 후보 생성
   - 실제 문장과 대화 속에 넣어 자연스러운지 검증

✅ **Evaluation**
   - 명확한 설명형 이름, 감정을 담은 이름, 새로운 브랜드형 이름 모두 가능
   - 모든 기준을 똑같이 충족할 필요는 없음
   - 기능이 위치한 맥락과 사용자에게 중요한 가치에 따라 기준의 우선순위를 결정

---

# 🧭 이름도 인터페이스의 일부다

사용자가 앱을 열고 별다른 설명 없이 어디로 가야 할지 아는 경험은 우연히 만들어지지 않는다.

레이아웃, 상호작용, 시각적 계층과 마찬가지로 이름도 그 경험을 설계하는 도구다.

이름은 대표 기능에만 필요한 것이 아니다.

- 앱과 제품 이름
- 주요 기능
- 메뉴
- 탭 바
- 설정
- 버튼
- 구독 플랜
- 데이터 레이블
- 상태와 옵션

이 모든 이름이 쌓여 앱의 언어를 만든다.

개별 이름 하나는 작은 결정처럼 보일 수 있지만, 반복되는 이름의 품질은 다음에 영향을 준다.

- 사용자가 기능을 찾는 속도
- 기능을 처음 접했을 때의 이해도
- 동작 결과에 대한 예측
- 앱에 대한 신뢰
- 브랜드의 인상
- 접근성과 현지화
- 다른 기능 이름과의 일관성

좋은 이름은 사용자가 멈춰서 의미를 해석하지 않아도 바로 다음 행동으로 이동하게 한다.

---

# ✅ 좋은 이름의 세 가지 기준

세션은 이름을 평가하는 세 가지 기준을 제시한다.

| 기준 | 핵심 질문 |
|---|---|
| Belongs | 이 이름이 앱의 기능, 문체, 기존 용어 체계 안에 자연스럽게 속하는가? |
| Expectations | 사용자가 이름을 보고 예상한 내용과 실제 기능이 일치하는가? |
| Works everywhere | 언어, 시장, 플랫폼, 화면 맥락이 달라도 의미와 사용성이 유지되는가? |

이 기준은 절대적인 규칙이 아니다.

제품에 따라 다음과 같은 추가 조건이 있을 수 있다.

- 상표권
- 산업별 규제
- 법률 용어
- 의료·금융 분야의 정확성
- 브랜드 전략
- 기존 제품군과의 관계
- 글자 수 제한
- 음성 인터페이스에서의 발음
- 현지 문화와 관용 표현

따라서 세 가지 기준은 정답표라기보다 선택과 절충을 판단하기 위한 도구다.

---

# 🧩 Belongs: 앱에 자연스럽게 속하는가

이름이 앱에 속한다는 것은 단순히 브랜드처럼 들린다는 의미가 아니다.

다음 요소들과 함께 자연스럽게 작동해야 한다.

- 사용자가 해당 위치에서 찾으려는 내용
- 같은 화면의 다른 이름
- 앱 전체에서 반복되는 핵심 용어
- 제품의 문체와 감정
- 메뉴나 탭의 계층
- 이름을 말하고 읽는 실제 상황

앱 내부에서 이미 특정 개념을 일관된 단어로 표현하고 있다면, 새 기능도 그 언어를 활용하는 것이 좋다.

예를 들어 앱 전체가 위치와 목적지를 `Places`라고 부르는데 새로운 기능만 `Locations`나 `Spots`라고 부르면, 각각의 단어가 자연스럽더라도 제품 전체의 언어는 흐려질 수 있다.

좋은 이름은 혼자 돋보이기보다 다른 이름들과 함께 하나의 체계를 만든다.

---

# 🎯 Expectations: 올바른 기대를 만드는가

사용자는 이름을 보는 순간 기능의 내용을 예측한다.

이름은 다음과 같은 질문에 미리 답해야 한다.

- 이 항목을 누르면 무엇이 나타나는가?
- 이 설정을 켜면 무엇이 바뀌는가?
- 이 값은 무엇을 의미하는가?
- 이 플랜은 다른 플랜과 어떻게 다른가?
- 이 기능이 나에게 어떤 결과를 주는가?

이름이 만든 기대와 실제 결과가 일치하면 신뢰가 쌓인다.

반대로 이름이 모호하거나 과장되어 있으면 사용자는 다음과 같은 불편을 겪는다.

- 기능을 사용하기 전에 추가 설명을 읽어야 함
- 잘못된 화면이나 동작을 예상함
- 선택하기 위해 비교와 해석에 더 많은 시간이 필요함
- 결과가 기대와 달라 실망함
- 민감한 맥락에서 평가받는 느낌을 받을 수 있음

특히 금융, 건강, 개인정보처럼 신뢰가 중요한 영역에서는 창의성보다 정확성, 중립성, 업계의 익숙한 표현이 우선할 수 있다.

---

# 🌍 Works everywhere: 모든 환경에서 작동하는가

앱의 이름은 한 화면과 한 언어에만 존재하지 않는다.

다음 환경에서도 같은 역할을 수행해야 할 수 있다.

- 다른 언어
- 다른 국가와 문화
- iPhone, iPad, Mac, Apple Watch, Apple TV
- 메뉴, 알림, 검색 결과, 위젯
- Siri와 음성 인터페이스
- 지원 문서와 마케팅 자료
- 작은 화면과 접근성 글자 크기
- 기능 이름을 포함한 문장

영어에서 간결하고 재치 있는 이름이라도 번역할 수 없거나 특정 문화에서 부정적인 의미가 생길 수 있다.

또한 명사처럼 보이는 이름이 실제 UI에서는 동작 버튼으로 사용되어 어색해질 수 있다.

이름을 평가할 때는 단어만 따로 보지 않고, 실제로 나타날 모든 문맥에 넣어 확인해야 한다.

---

# 💳 Apple Cash 사례: Balance

Apple Cash에서 사용자가 송금하기 전에 가장 먼저 알아야 하는 정보는 현재 사용할 수 있는 금액이다.

이 값을 어떤 이름으로 표시할지 여러 후보를 비교한다.

## Spending Power

`Spending Power`는 강하고 매력적으로 들릴 수 있지만 구체적이지 않다.

사용자는 다음과 같이 해석할 수 있다.

- 신용 한도
- 평가 점수
- 소비 능력
- 추천 지출액
- 현재 보유한 현금

또한 값이 낮거나 0일 때 단순한 데이터 레이블이 아니라 사용자를 평가하는 표현처럼 느껴질 수 있다.

금융 서비스는 높은 신뢰를 요구한다. 의도하지 않은 판단이나 모호함도 신뢰를 손상할 수 있다.

## Current Funds

`Current Funds`는 의미상 현재 계정에 있는 돈을 설명한다.

하지만 실제 대화에 넣으면 자연스럽지 않다.

> Let me check my Current Funds.

스프레드시트나 회계 문서의 용어처럼 느껴지며, 일상적으로 송금하고 돈을 받는 서비스의 언어와 어울리지 않는다.

## Balance

최종 이름은 `Balance`다.

이 이름은 다음 이유로 적합하다.

- 금융 업계에서 널리 쓰임
- 사용자가 의미를 이미 알고 있음
- 명확하고 중립적임
- 값을 평가하거나 감정을 부여하지 않음
- 다른 언어에서도 대응되는 익숙한 금융 용어가 있음
- 기능의 위치와 목적에 정확히 맞음

이 사례는 가장 독창적인 단어보다 이미 역할을 잘 수행하는 익숙한 단어가 더 좋은 선택일 수 있음을 보여준다.

# ⚖️ 명확성과 브랜드 사이의 선택

세션은 헬스장 앱의 구독 플랜을 예로 든다.

## 명확한 이름

- Basic Access
- All Access

두 플랜의 차이를 비교적 쉽게 예상할 수 있다.

## 브랜드를 강조한 이름

- Lightweight
- Heavyweight

운동 브랜드와 잘 어울리고 재미있지만, 사용자는 실제 혜택 차이를 바로 알기 어렵다.

`Lightweight`가 저렴한 플랜인지, 초보자용인지, 운동 강도가 낮다는 뜻인지 추가로 해석해야 한다.

그렇다고 브랜드형 이름이 반드시 잘못된 것은 아니다.

중요한 것은 선택에 따른 비용을 이해하는 것이다.

| 선택 | 장점 | 추가로 필요한 작업 |
|---|---|---|
| 명확한 이름 | 빠르게 이해하고 비교 가능 | 브랜드 표현이 약할 수 있음 |
| 표현적인 이름 | 기억에 남고 브랜드와 잘 맞음 | 설명, 보조 텍스트, 온보딩이 더 필요할 수 있음 |

모든 이름이 세 가지 기준을 완벽하게 충족할 필요는 없다.

기능이 어디에 있고, 어떤 결정을 돕고, 잘못 이해했을 때 어떤 문제가 생기는지를 고려해 우선순위를 정해야 한다.

# 👤 기술이 아니라 사용자에게서 출발하기

제품을 만드는 사람은 기능을 다음 기준으로 이름 붙이기 쉽다.

- 내부 구현
- 사용한 기술
- 알고리즘
- 데이터 구조
- 기능이 수행하는 기계적 동작
- 프로젝트 내부 코드명

하지만 사용자는 기술을 사용하러 오는 것이 아니라 기술이 자신에게 제공하는 결과를 얻으러 온다.

따라서 이름을 만들기 전에 먼저 대상 사용자를 구체적으로 정의해야 한다.

예를 들면 다음과 같다.

- 처음 아이를 키우는 부모
- 마라톤을 준비하는 사람
- 매일 사진을 기록하는 사람
- 소음을 줄이고 팟캐스트를 듣고 싶은 사람
- 이전에 방문한 장소를 다시 찾으려는 사람

대상이 분명해지면 이름의 기준도 추상적인 원칙에서 실제 판단 도구로 바뀐다.

# 💭 Think, Feel, Do 연습

세션은 Apple Maps의 방문 장소 기능을 예로 들어 이름을 만드는 워크숍을 제시한다.

기능은 사용자가 이전에 방문했던 카페, 공원, 장소를 기억하고 다시 찾게 해준다.

팀은 대상 사용자를 생각하며 다음 세 영역에 아이디어를 적는다.

## Think

사용자가 기능을 접했을 때 무엇을 생각하기를 원하는가?

예시는 다음과 같다.

- 사용하기 쉽다
- 유용하다
- 영리하다
- 내가 잊은 장소도 찾아준다
- 다시 검색할 필요가 없다
- 내 기록이 잘 정리되어 있다

이 단계에서는 완성된 이름을 찾지 않는다.

가능한 한 많은 생각을 적고 반복되는 방향을 발견하는 것이 목적이다.

## Feel

사용자가 어떤 감정을 느끼기를 원하는가?

예시는 다음과 같다.

- 잊었던 장소를 다시 발견하는 즐거움
- 반가움
- 안심
- 내 정보가 보호된다는 신뢰
- 개인적인 기록이라는 친밀감
- 기능이 나를 돕고 있다는 느낌

기능의 가치가 실용적인 편리함만이 아니라 감정과 개인정보 보호에 있을 수도 있다.

## Do

사용자가 실제로 어떤 행동을 하기를 원하는가?

예시는 다음과 같다.

- 기능을 쉽게 찾기
- 이전 장소 검색하기
- 장소 다시 방문하기
- 다른 사람과 장소 공유하기
- 기록을 탐색하기
- 필요할 때 신뢰하고 사용하기

행동을 정의하면 이름이 사용자를 올바른 다음 단계로 이끄는지 평가할 수 있다.

# 🗂️ 아이디어를 주제로 묶기

Think, Feel, Do에서 충분한 아이디어를 모은 다음 반복되는 단어와 감정을 묶는다.

Apple Maps 사례에서는 세 가지 핵심 주제가 나타났다.

| 주제 | 의미 |
|---|---|
| Ease | 별다른 노력 없이 원하는 장소를 찾는 편리함 |
| Excitement | 좋아했던 장소를 다시 발견하는 즐거움 |
| Security | 기록이 비공개이며 보호된다는 신뢰 |

이 주제는 이름 후보를 평가하는 구체적인 기준이 된다.

후보가 다음 질문에 답하는지 확인할 수 있다.

- 쉽게 이해되는가?
- 다시 발견하는 감정을 전달하는가?
- 불필요하게 불안하거나 침해적으로 들리지 않는가?
- Apple Maps의 기존 언어와 어울리는가?
- 번역했을 때 핵심 의미가 유지되는가?

일부 후보는 앱과 어울리지 않거나, 지나치게 모호하거나, 다른 언어에서 사용하기 어려워 이 단계에서 제외할 수 있다.

# 💬 실제 문장에 넣어보기

후보 이름은 목록에서 읽을 때와 실제 인터페이스에서 사용할 때 다르게 느껴질 수 있다.

세션은 후보를 사용자가 읽거나 말할 법한 문장에 넣어보라고 권한다.

예를 들면 다음과 같다.

> Hey, check out Private Memories.

> Just search for Private Memories.

이 테스트를 통해 다음을 확인할 수 있다.

- 자연스럽게 발음되는가?
- 문법적으로 어색하지 않은가?
- 지나치게 길지 않은가?
- 음성으로 들었을 때 다른 단어로 오해되지 않는가?
- 기능보다 다른 의미가 먼저 떠오르지 않는가?
- 앱 안의 문장과 지원 문서에서 반복 사용하기 쉬운가?

자연스럽게 읽히고 말할 수 있는 이름은 추가로 검토할 가치가 있다.

---

# 🗺️ Apple Maps 사례: Visited Places

Apple Maps 팀은 최종적으로 `Visited Places`를 선택했다.

이 이름이 적합한 이유는 다음과 같다.

- 방문한 장소라는 기능을 직접 설명
- Maps가 이미 사용하는 `Places`라는 용어와 일관됨
- 사용자의 장소라는 소유 관계가 자연스럽게 드러남
- 개인정보 보호를 과장된 표현 없이 뒷받침
- 다양한 언어로 옮기기 쉬움
- 검색과 인터페이스 문장에 넣었을 때 자연스러움

이 이름은 Ease, Excitement, Security를 모두 화려하게 표현하지 않는다.

대신 기능을 이해시키고 앱의 언어에 속하며, 개인정보에 대한 올바른 기대를 만드는 쪽을 선택한다.

---

# ✨ 설명형 이름만이 정답은 아니다

앞선 사례는 대체로 직접적이고 설명적인 이름이다.

하지만 모든 기능이 같은 접근을 사용해야 하는 것은 아니다.

앱과 기능의 관계에 따라 감정적이거나 새로운 이름이 더 적합할 수 있다.

세션은 세 가지 유형을 보여준다.

| 유형 | 사례 | 명확성이 만들어지는 방식 |
|---|---|---|
| 설명형 | Enhance Dialogue | 기능과 결과를 직접 설명 |
| 감정형 | Memories | 사용자가 느끼는 경험으로 의미 전달 |
| 브랜드형·조합형 | AutoMix | 익숙한 단어의 조합으로 새로운 개념 전달 |

기준은 같지만 기준을 충족하는 방식은 달라질 수 있다.

---

# 🖼️ Photos 사례: Memories

Photos에는 사진 보관함을 분석해 중요한 순간을 자동으로 보여주는 기능이 있다.

기술적으로는 알고리즘이 사진을 그룹화하고 추천하는 기능이다.

하지만 사용자는 기능을 다음처럼 경험한다.

- 잊고 있던 생일 사진
- 예전 여행
- 평범했지만 기억할 가치가 있었던 하루
- 오래전에 들었던 누군가의 웃음
- 다시 만나게 된 소중한 순간

사용자는 알고리즘을 찾는 것이 아니라 기억을 다시 만난다.

따라서 `Memories`는 기술적 설명보다 사용자의 감정을 이름으로 삼는다.

이 이름의 명확성은 기능을 상세히 설명하는 데서 나오지 않는다.

Photos 앱의 분위기와 사용자가 사진에 맺는 관계를 정확히 포착하기 때문에 이해된다.

---

# 🎧 Apple Podcasts 사례: Enhance Dialogue

Apple Podcasts에는 목소리를 분리해 배경 소음을 줄이면서 원본 오디오를 변경하지 않는 기능이 있다.

세션은 여러 후보를 순서대로 평가한다.

## Vocal Isolation

오디오 기술을 설명하는 명사다.

하지만 사용자가 얻는 경험보다 내부 처리 방식에 초점이 있다.

## Isolate Vocals

동사형으로 바꾸어 사용자가 수행하는 동작처럼 만든다.

명사보다 제어감을 주지만 여전히 오디오 엔지니어링 용어에 가깝다.

## Clarify Speech

사용자가 얻는 결과에 더 가까워진다.

그러나 기능이 제공하는 경험 전체를 충분히 설명하지 못한다.

## Enhance Playback

기능이 적용되는 대상이 넓고 모호하다.

무엇이, 누구를 위해 향상되는지 알기 어렵다.

## Enhance Dialogue

최종 이름은 다음 질문에 답한다.

- 무엇이 향상되는가? → Dialogue
- 어떤 동작인가? → Enhance

메뉴 안에서 동작형 이름으로 자연스럽게 작동하고, 기능을 켰을 때 약속한 결과를 제공한다.

또한 유사한 기능에 Apple TV에서도 같은 이름이 사용되어 Apple 제품군의 언어와도 일관된다.

---

# 🎵 Apple Music 사례: AutoMix

Apple Music의 `AutoMix`는 곡 사이를 DJ처럼 자연스럽게 이어 재생이 멈추지 않게 하는 설정이다.

이 이름은 기존 단어 하나를 선택한 것이 아니라 두 단어를 결합해 만든다.

- `Auto`: 사용자가 직접 조작하지 않아도 자동으로 실행
- `Mix`: 곡을 서로 이어 섞음

`AutoMix`라는 단어가 기존에 없더라도 구성 요소가 익숙하기 때문에 의미를 바로 추론할 수 있다.

이 사례는 의도적인 이름 짓기가 반드시 사전에 있는 단어만 사용해야 한다는 뜻은 아님을 보여준다.

새로운 이름도 다음 조건을 만족하면 명확할 수 있다.

- 익숙한 단어로 구성됨
- 각 단어의 역할이 분명함
- 실제 기능과 직접 연결됨
- 읽고 발음하기 쉬움
- 추가 설명 없이 기본 의미를 추론할 수 있음

---

# 🏷️ 이름 유형별 비교

| 이름 유형 | 장점 | 주의할 점 | 사례 |
|---|---|---|---|
| 업계 표준형 | 즉시 이해되고 신뢰가 높음 | 브랜드 표현이 적을 수 있음 | Balance |
| 직접 설명형 | 기능과 결과를 쉽게 예측 | 길거나 일반적으로 느껴질 수 있음 | Visited Places, Enhance Dialogue |
| 감정 중심형 | 사용자의 관계와 감정을 표현 | 앱 맥락이 없으면 모호할 수 있음 | Memories |
| 브랜드형 | 기억에 남고 제품 개성을 표현 | 학습 비용과 설명이 필요할 수 있음 | Lightweight, Heavyweight |
| 합성어형 | 새로운 개념을 간결하게 표현 | 구성 단어만으로 의미가 전달되어야 함 | AutoMix |

이름 유형을 먼저 정할 필요는 없다.

후보를 만든 뒤 사용자의 필요와 기능의 맥락에 가장 적합한 방식이 무엇인지 판단할 수 있다.

# 🔍 이름 평가 질문

후보를 검토할 때 다음 질문을 사용할 수 있다.

## Belongs

- 앱의 문체와 어울리는가?
- 같은 화면의 다른 이름과 일관되는가?
- 기존 핵심 용어를 활용하는가?
- 제품군의 비슷한 기능과 같은 이름을 사용할 수 있는가?
- 실제 대화에서 자연스럽게 말할 수 있는가?

## Expectations

- 이름만 보고 기능의 결과를 예상할 수 있는가?
- 기능을 켜거나 눌렀을 때 그 기대를 충족하는가?
- 기술이 아니라 사용자가 얻는 가치를 표현하는가?
- 부정적인 판단이나 압박으로 느껴질 가능성이 없는가?
- 이름 때문에 추가 설명이 과도하게 필요하지 않은가?

## Works everywhere

- 번역 가능한가?
- 다른 언어에서 지나치게 길어지지 않는가?
- 문화적으로 다른 의미나 부정적인 연상이 없는가?
- 음성으로 말하고 들을 때 구분 가능한가?
- 메뉴, 알림, 검색 결과, 지원 문서에서 모두 자연스러운가?
- 다른 Apple 플랫폼의 인터페이스에서도 사용할 수 있는가?

---

# 🛠️ 이름을 만드는 워크숍

세션의 과정을 팀 작업으로 옮기면 다음과 같이 진행할 수 있다.

## 1단계: 맥락 정의

- 이름을 붙일 대상
- 화면에서의 위치
- 사용자가 수행하는 작업
- 잘못 이해했을 때의 위험
- 기존 관련 용어
- 대상 사용자

## 2단계: Think, Feel, Do 작성

한 장의 메모에는 하나의 생각만 적고, 초반에는 걸러내지 않는다.

### Think
사용자가 무엇을 이해하거나 믿기를 원하는가?

### Feel
사용자가 어떤 감정과 신뢰를 느끼기를 원하는가?

### Do
사용자가 다음으로 어떤 행동을 하기를 원하는가?

## 3단계: 반복 주제 묶기

비슷한 생각을 그룹화하고 주요 가치와 감정을 정리한다.

## 4단계: 후보 생성

다음과 같은 여러 방향으로 후보를 만든다.

- 업계 표준 용어
- 직접적인 설명
- 결과 중심 표현
- 감정 중심 표현
- 브랜드 언어
- 두 단어를 결합한 새로운 이름

## 5단계: 문맥 테스트

후보를 다음 위치에 넣는다.

- 실제 버튼
- 메뉴
- 탭 바
- 설정 설명
- 알림
- Siri 요청
- 지원 문서
- 일상 대화

## 6단계: 기준 평가

Belongs, Expectations, Works everywhere를 기준으로 비교한다.

## 7단계: 우선순위와 절충 결정

모든 기준을 충족하지 못하더라도 기능에 가장 중요한 기준을 선택한다.

---

# ⚠️ 피해야 할 접근

## 내부 기술 이름을 그대로 사용

구현을 설명하지만 사용자에게 필요한 결과를 설명하지 못할 수 있다.

## 지나치게 모호한 브랜드 이름

기억에는 남지만 기능 선택과 탐색에 마찰을 만든다.

## 과장된 이름

실제 결과가 이름이 만든 기대에 미치지 못하면 신뢰를 손상한다.

## 판단을 포함하는 이름

사용자의 값이나 상태를 평가하는 느낌을 줄 수 있다.

## 기존 용어 체계와 다른 동의어 남용

비슷한 개념에 여러 이름을 사용하면 사용자는 서로 다른 기능으로 오해할 수 있다.

## 단어만 따로 평가

실제 UI 문장, 음성, 번역에서 어색할 수 있다.

## 현지화를 마지막에 확인

영어에서만 가능한 말장난이나 합성 구조라면 다른 언어에서 기능명 체계가 무너질 수 있다.

---

# 🗣️ 이름이 앱의 언어를 만든다

좋은 이름 하나를 선택하면 다음 이름을 만드는 일이 쉬워진다.

이름들이 서로 기준과 용어를 제공하기 때문이다.

시간이 지나면 다음과 같은 공통 규칙이 형성된다.

- 어떤 개념에 어떤 단어를 사용하는가
- 기능은 명사형과 동사형 중 어떤 방식을 따르는가
- 메뉴와 버튼의 문체
- 브랜드 표현의 강도
- 개인정보와 신뢰를 표현하는 방식
- 비슷한 기능을 묶는 언어
- 사용자에게 직접 말하는 방식

이렇게 쌓인 이름은 앱의 언어 체계가 된다.

일관된 언어는 사용자가 새로운 기능을 처음 접해도 기존 경험을 바탕으로 의미를 예상할 수 있게 한다.

---

# 📋 이름 검토 체크리스트

## 앱과의 적합성

- [ ] 앱의 전반적인 문체와 어울린다
- [ ] 같은 화면과 기능군의 다른 이름과 일관된다
- [ ] 기존에 사용하는 핵심 용어를 불필요하게 바꾸지 않는다
- [ ] 이름을 실제 문장으로 말했을 때 자연스럽다
- [ ] 브랜드 표현이 기능 이해를 방해하지 않는다

## 기대와 신뢰

- [ ] 이름만 보고 무엇을 하는 기능인지 예측할 수 있다
- [ ] 실제 기능이 이름이 만든 기대를 충족한다
- [ ] 내부 기술보다 사용자가 얻는 결과를 표현한다
- [ ] 과장되거나 모호하지 않다
- [ ] 사용자를 평가하거나 압박하는 뉘앙스가 없다
- [ ] 민감한 분야에서는 업계 표준 용어를 우선 검토했다

## 언어와 플랫폼

- [ ] 주요 지원 언어로 자연스럽게 번역할 수 있다
- [ ] 다른 문화에서 부정적인 의미가 없는지 확인했다
- [ ] 작은 화면과 접근성 크기에서도 사용할 수 있다
- [ ] 음성으로 말하고 들었을 때 이해할 수 있다
- [ ] 메뉴, 알림, 검색, 위젯, 지원 문서에서도 작동한다
- [ ] 다른 플랫폼에서 유사 기능과 이름이 충돌하지 않는다

## 검증 과정

- [ ] 대상 사용자를 구체적으로 정의했다
- [ ] Think, Feel, Do를 작성했다
- [ ] 반복되는 주제와 핵심 가치를 정리했다
- [ ] 설명형, 감정형, 브랜드형 등 여러 방향의 후보를 만들었다
- [ ] 실제 인터페이스와 문장에 후보를 넣어 확인했다
- [ ] 어떤 기준을 우선하고 무엇을 절충했는지 기록했다
- [ ] 현지화 담당자와 초기 단계에서 검토했다

# 핵심 메시지

이름 짓기는 레이아웃, 상호작용, 색상과 마찬가지로 앱 경험을 구성하는 기본적인 디자인 작업이다.

좋은 이름은 기능이 무엇인지 설명하는 데 그치지 않고, 그 기능을 사용하는 사람에게 필요한 의미와 기대를 전달한다.

이름이 앱에 자연스럽게 속하고, 실제 기능에 맞는 기대를 만들며, 언어와 플랫폼이 달라도 유지될 때 사용자는 앱을 더 쉽게 이해하고 신뢰할 수 있다.

각 이름은 독립적인 결정이 아니라 다음 이름의 기준이 된다. 이렇게 축적된 이름은 시간이 지나면서 앱 전체의 언어를 형성한다.
